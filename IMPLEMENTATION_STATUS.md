The Markdown editor has a collection version (409 on conflict); forgetting deletes the row and its index entry. |
| AUTO-01 | Implemented | One-time, daily, and weekly schedules with prompt, allowed accounts, IANA zone, enabled flag, next and last run. The owner previews the normalized schedule and next three runs before activating; automations the assistant proposes stay inactive until the owner confirms them through the authenticated API. Runs are `occurrences` rows keyed by `(automation_id, scheduled_for)` and inserted with `ON CONFLICT DO NOTHING`; due automations are claimed with `FOR UPDATE SKIP LOCKED`. Spring-forward gaps run at the first valid time afterward; repeated fall-back hours run once. A missed one-time run runs once, marked late; missed recurring runs coalesce into one catch-up run that reports the missed count. Scheduled runs may use only the automation's accounts (enforced by the broker), and writes still need approval. |

The first sync records a baseline and alerts nothing. Only additions, cancellations, moves, renames, and relocations touching the next 48 hours count; each event version is recorded once in `provider_events`; changes wait for a 60-second quiet period and are combined into one run. The automation's own approved calendar edits are recognised by event ID and etag and never re-trigger it. Event text is untrusted: it never enters the run's instruction and is read through `automation.trigger_details`. |

## M2 boundary verification

- **Database roles:** `opa db-roles` creates `opa_app` and `opa_broker`. Tests confirm the app role cannot read the `broker` schema, and the broker role cannot read password hashes, task intents or checkpoints, message content, sessions, or event payloads. A complete propose, approve, and send flow passes with the broker connected as `opa_broker`.
- **Egress proxy policy:** the worker's proxy tunnels only allowlisted host:port pairs, refuses plain HTTP forwarding, and refuses allowlisted names that resolve to private addresses. Address classification covers loopback, RFC 1918, link-local and metadata, CGNAT, IPv6 unique-local, and IPv4-mapped IPv6.
- **Mutation check:** removing the broker's payload-hash comparison makes the tamper test fail, so it is not passing vacuously. Removing the broker's "task must be running" check does not fail any test, because cancellation and lease fencing each block the same paths first; that check is defense in depth.

## M3 verification

- **Against a fake, not Google.** `tests/fake_google.py` implements Google's OAuth, Gmail, and Calendar HTTP behavior in-process: PKCE check, single-use codes, exact redirect URI, client authentication, bearer expiry on the test clock, per-endpoint scopes, etag preconditions, and injected faults. 28 M3 tests run the real API callback, broker, adapter, and worker against it.
- **Live Google has not been called.** The live check was skipped as instructed. `server/scripts/live_smoke_google.py` is written and refuses to run without `LIVE_SMOKE=1`; it has never been run.
- **Mutation checks:** removing the refresh row lock, the callback's session binding, or the "5xx on a write is unknown" rule each makes its test fail.
- **One unexplained hang** occurred once during the mutation run and did not reproduce in seven later full runs. Every test now has a 60-second limit so a hang fails and names the test.

## M5 verification

- **End-to-end scenario (spec section 12).** `test_m5_end_to_end.py` runs the whole scenario on the fixture provider with the scripted model: the owner previews and confirms a weekday 18:00 schedule plus a calendar-change trigger; the first poll records a baseline; the 18:00 run reads the calendar, relevant email, and an uploaded file, writes a sourced brief with an explicit unknown, renders a PDF, and proposes an email with that exact PDF version attached; nothing is sent until the owner approves; the sent message carries the approved bytes and a provider reference. A moved meeting then creates exactly one revision run, which edits the brief, re-renders the same PDF as a new version, and proposes a new email that again waits for approval. Later polls create no alert loop.
- **Mutation checks.** Removing each of these makes its test fail: the overlap check, own-edit suppression, the provider-event dedup record, DST gap handling, the broker's per-task account limit, and the combination of row locking and the unique occurrence key.
- **Browser smoke.** `scripts/ui_smoke.py` now also creates a weekday schedule through the form, checks the preview and its three upcoming runs, confirms it, turns it off, and deletes it.
- **Calendar sync through the Google adapter.** `test_m5_google_trigger.py` runs a trigger in live mode against the fake Google: a paged initial sync with `timeMin`, incremental requests with `syncToken` and `showDeleted`, a moved event, a cancelled event returned as a minimal entry without times, and an expired token (HTTP 410) followed by a full resync that fires nothing. Removing the broker's resync handling makes it fail. An off-by-one in the fake's token expiry first made this path look covered when it was not; that was found and fixed.
- **Mutation checks (continued).** The resync mutation above is also caught.

## Not verified / known limitations

- **Docker Compose has not been run.** Docker is not installed on the development machine. `deploy/compose.yaml` parses and its anchors resolve, but images have not been built.
- Compose now declares the broker, egress proxy, database roles, and isolated networks, but it has not been run, so the network half of T-NET-01 (the worker cannot reach any host except through the proxy) is unverified. The proxy's policy half is tested.
- No real Google API has been called. Differences between the fake and Google (error payload details, MIME edge cases, rate-limit behavior) are possible until the live check is run.
- The Google connect flow is tested at the API level; the browser smoke covers the demo account only.
- **Follow-up from merging M3 and M4:** email attachments are still refused for Google accounts because the Gmail adapter does not build MIME attachments yet. M4 planned this for when M3 merged; it was not part of M5. The end-to-end scenario therefore passes on the fixture provider only.
- M4: Compose now mounts an `artifacts` volume (read-write for api and worker, read-only for broker), but it has not been run. The PDF extraction child is time- and CPU-limited but not network- or seccomp-sandboxed. Built-in PDF fonts cover Latin-1 only. Artifact and memory tool calls are not deduplicated if the worker crashes between the tool's commit and the checkpoint. `opa artifacts-gc` now runs hourly inside `opa scheduler` (M5). No axe-core scan or VoiceOver pass was run on the new screens (A17 is M6).
- M5: the scheduler polls every 15 seconds, so a run can start up to 15 seconds after its time (runs over 2 minutes late are marked late). Calendar triggers poll every 5 minutes, so a change is noticed within about 5 minutes plus the 60-second quiet period. The Google calendar sync path is tested against the fake Google, not real Google. An automation whose previous run is waiting for approval holds its next runs until that run finishes; the owner is notified once. The trigger's baseline is kept in the automation row and covers events from one day ago to 60 days ahead.
- The Anthropic adapter has not been exercised against the live API (no key configured). It is code-complete but unverified.
- Frontend API types are hand-written; generating them from OpenAPI is scheduled for M6.
- SSE delivery polls the outbox every 500 ms rather than using `LISTEN/NOTIFY`. Correct but adds up to half a second of latency.
- Local-toolchain note: Rollup's native addon crashes under LingCode's embedded Node, so `web/package.json` overrides Rollup with its WebAssembly build. Standard Node installs are unaffected.
